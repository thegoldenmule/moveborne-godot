# Validator Service

Real-time game-state validation service, copied from the Moveborne project and
made self-contained for this repo. It validates moves, verifies state hashes, and
exposes an MCP server for inspecting and debugging match state.

The game-facing API is a **gRPC request/response service**
(`moveborne.validator.v1.ValidatorService`: `InitMatch`, `ValidateAction`,
`CompleteMatch`) whose message types live in **`protos/`** — the single source
of truth for the wire format. In production the game reaches it through the
**Snapser Hermes WebSocket** (`wss://gateway.snapser.com/<snapend>/v1/hermes/ws?token=<session>`,
`MESSAGE_TYPE_SNAP_API_PROXY` → the snap's gRPC port); locally the validator
serves the identical envelope itself at `ws://localhost:5555/hermes/ws?token=<player-id>`,
so the game client has exactly one codepath. GDScript bindings are generated
from the same protos by godobuf (`game/net/proto/`, see its README).

Game state and actions stay **canonical JSON inside proto string fields**: the
determinism hash is computed over canonical JSON (byte-for-byte parity between
the TS logic dist and the GDScript port), so the wire format must not re-model
them.

## Layout

```
validator/
├── package.json          # Bun workspace root (workspaces: src/*)
├── protos/               # protobuf wire protocol (validator messages + Hermes envelope)
│   ├── moveborne/validator/v1/   # validator.proto (service) + validator_messages.proto
│   └── hermes/                   # hermes_envelope.proto (ClientMessage/ServerMessage)
├── .env.example          # config template (real .env lives in src/validator/)
├── src/
│   ├── validator/        # the service (Bun + Hono + gRPC + Hermes WS + MCP)
│   └── logic/            # @spyre-io/moveborne-logic — game rules (workspace dep)
```

`src/validator` depends on `src/logic` via the `workspace:*` protocol; Bun links
it automatically on `bun install`. `src/logic/dist` is committed so the service
runs without a build step (rebuild with `bun run build` when the logic changes).

### Regenerating from the protos

`validator/protos/` is the single source of truth. Three artifacts are generated
from it and committed; regenerate them all whenever a `.proto` changes:

```bash
tools/gen-protos.sh            # from the repo root (needs the Godot binary)
tools/gen-protos.sh --skip-gdscript   # JS SDK + swagger only, no Godot
```

It produces:
1. **JS SDK** — `src/validator/proto-gen/validator-descriptor.json`, the compiled
   protobufjs descriptor the validator loads at runtime (`proto.ts`, via
   `Root.fromJSON` — no `.proto` text parse at startup). Regenerate alone with
   `bun run gen:sdk`.
2. **swagger.json** — the OpenAPI spec Snapser uploads on `byosnap publish`
   (powers the API Explorer, SDK generation, and the gateway's per-route auth).
   Version is pulled from `package.json`. Regenerate alone with `bun run gen:swagger`.
   After regenerating, redeploy so Snapser picks it up (`snapctl byosnap publish` + `sync`).
3. **GDScript bindings** — `game/net/proto/*_pb.gd` (godobuf); see
   `game/net/proto/README.md`.

`grpc.ts` still reads `validator.proto` via `@grpc/proto-loader` for the gRPC
*service definition* (which the message descriptor does not carry).

## Setup

```bash
cd validator
bun install                       # installs deps + links the logic workspace
cp src/validator/.env.example src/validator/.env   # already present; edit as needed
```

For production, set a strong secret in `src/validator/.env`:

```bash
VALIDATOR_SHARED_SECRET=$(openssl rand -hex 32)
```

Auth has no bypass switch: every RPC binds the gateway-validated `User-Id` to
the match owner (`player_id`). Locally there's no gateway, so the Hermes-emulation
endpoint takes the self-stamped player id as its `?token=` query param (the game
and the headless tests do this); api-key/internal callers pass without user binding.

## Run

```bash
cd validator
bun run dev      # hot-reload (bun --watch), uses PORT from .env (5555)
# or
bun run start
```

Ports (local defaults; deployed: HTTP `:8080`, gRPC `:8081` per the BYOSnap profile):

- Health:    `GET  http://localhost:5555/health`
- Status:    `GET  http://localhost:5555/api/status`
- Hermes WS: `ws://localhost:5555/hermes/ws?token=<player-id>` (binary protobuf envelope)
- gRPC:      `localhost:8081` — `moveborne.validator.v1.ValidatorService`
- History:   `POST /api/match/{init-from-history,save-history}`, `GET /api/match/load-history/:id`
- MCP:       `POST http://localhost:5555/mcp`

Tests: `cd src/validator && bun test` (service handlers against the real golden
vectors, Hermes envelope dispatch) and `bun run test` at the workspace root for
the logic package. The game-side counterparts are
`game/tools/test_validator_client.gd` (local E2E through the emulated Hermes WS)
and `game/tools/verify_hermes_proto.gd` (godobuf ⇄ protobufjs byte parity;
fixture regenerated by `src/validator/tools/generate-hermes-golden.ts`).

## Story catalog (content pipeline)

`validator/content/story_catalog.json` is the **one hand-edited** catalog. It is
the validator's **runtime source via Remote Config**, NOT bundled in the image
(see the ADR superseding ADR-23's bundled-image clause):

- **Runtime:** at boot the validator pulls app-config `v1` (key `story_catalog`)
  from the Remote Config snap over s2s (`SNAPEND_REMOTE_CONFIG_HTTP_URL` +
  `Gateway` header; api-key fallback; committed-file fallback only in local dev),
  validates + caches it, refreshes on a TTL, and serves **last-known-good** on a
  refresh failure. `content/story_catalog.json` is `.dockerignore`d. Force a
  re-fetch with `POST /api/story/catalog/refresh`; the loaded version shows in
  `GET /api/status` (`story_catalog_version`).
- **Per-match pin:** a story match is graded against the `catalog_version` it was
  initialized with for its whole life (init handshake reconciles client vs
  validator; mismatch → `FAILED_PRECONDITION catalog_version_mismatch`).
- **Client baked copy:** `bun run sync:catalog` generates
  `game/story/story_catalog.json` from the canonical file (byte-verified by
  `verify_story_catalog.gd`); `bun run sync:catalog:check` guards drift.
- **Publishing** (no write API — manual console paste): `bun run tools/story-appconfig.ts emit`
  prints the payload; `… verify` deep-compares the live config to the committed
  catalog; `… status` reports `catalog_version` across committed / live / deployed.
  The Story Map editor dock has a "Catalog ⇄ Remote Config" panel that wraps
  verify + copies the publish payload.

## Use from Claude Code

This repo is already wired to use the validator:

- `.mcp.json` registers the `validator` MCP server at `http://127.0.0.1:5555/mcp`.
- `.claude/settings.local.json` enables it.
- The `run-validator` skill (`.claude/skills/run-validator/`) starts, stops, and
  inspects the service. Its `start-validator.sh` launches the validator on 5555.

Start the validator first (so the MCP server is reachable), then the
`mcp__validator__*` tools become available for listing matches, inspecting state,
simulating actions, and reading state history.
