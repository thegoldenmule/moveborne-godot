# Feature: Story Mode — worlds, level maps, star goals & progression

**Status:** shipped

## Summary
Story Mode turns the existing single-button story launch (game/ui/screens/home.gd:48, hardcoded scenario_id 0) into a worlds-and-levels progression. A candy-crush-style linear map screen (new StoryMapState pushed on the UiRouter between ShellState and MatchState) shows each world's levels, earned stars, locks, and the next playable level; tapping Play threads {mode: story, level_id, scenario_id, goals} through GameState.next_match into the existing MbMatch/validator flow unchanged. Level/world content lives in ONE committed JSON catalog — worlds → levels → scenario_id mapping, 3 goals per level (points or max_tile, each with an optional time_limit_s), and per-star rewards — uploaded to the Snapser Remote Config snap as app-config and baked into the client as the offline/dev fallback; the validator loads the same catalog. Star grading is validator-authoritative: CompleteMatch (validator/src/validator/service.ts) grades the final validated SynchronizedGameState (score, max tile from tiles, elapsed wall-clock from StoredMatch.created_at) against the level's goals, writes per-user progress (stars, unlocks, rewarded_stars watermark) to a Storage-snap user json-blob via s2s, grants per-star currency deltas through the existing Inventory s2s path, and returns a story_result_json the client renders as a level-result screen. Completing ≥1 goal earns 1 star and unlocks the next level; all 3 goals earn 3 stars. Goal evaluation is strictly post-match and outside game/logic/, so determinism parity (golden hashes, the byte-for-byte TS port) is untouched — the reserved SynchronizedGameState.level field is deliberately NOT used. Prerequisites: provision remote-config + storage snaps on snapend c4n1awfs (absent from snapser/snapend-manifest.json today) and a small proto extension (InitMatchRequest.level_id, CompleteMatchResponse.story_result_json) with godobuf regeneration.

## Design constraints
1. Determinism parity wall: NO goal/star/progression logic in game/logic/, NO new or repurposed fields in the hashed SynchronizedGameState (the reserved level field stays unused), scenario configs untouched; all existing verify_*.gd parity verifiers must still PASS unchanged
2. Server-authoritative grading: stars/rewards/unlocks computed only by the validator from its OWN validated state and timestamps; the Storage progress blob is written s2s only (client read-only) — consistent with gateway User-Id binding and the open self-grant hardening finding
3. Goal evaluation is post-match only (CompleteMatch), so it needs no engine changes and no new golden-hash domain; elapsed time = StoredMatch.created_at → CompleteMatch arrival; validator state is in-memory, so grading must happen in-session
4. Wire convention: game state and story results stay canonical-JSON strings inside proto fields; any proto change requires godobuf regeneration per game/net/proto/README.md; do not change the deployed external port
5. Story is online-only (anonymous Snapser sign-in, Hermes WSS token-in-query); Infinite remains fully offline and grants nothing — unchanged
6. Reward idempotency: keep the per-match rewards_granted latch AND add a per-level rewarded_stars watermark in the progress blob so replays grant only newly-earned star tiers; stars are max-monotonic
7. Snapend dependency: remote-config and storage snaps are NOT in snapser/snapend-manifest.json — provisioning on c4n1awfs must precede any live testing; the client must fall back to the baked catalog when fetch fails
8. Wiki content is authored ONLY via the wiki MCP (mutatePage/mutatePageBatch) — never edit the emitted wiki/*.md mirror on disk
9. Repo conventions: commit directly to main; commit the catalog JSON and any golden vectors (never hand-write expected values); the validator Docker build context must be validator/
10. Catalog levels may only reference existing MbScenarios.SCENARIOS ids (0–17); authoring NEW scenarios requires TS-first work in ~/projects/thegoldenmule/moveborne plus regenerated goldens — out of scope for v1
11. Verification etiquette: automated checks are headless/driver-level (verify_*.gd, MbUi/MbDebug, validator MCP); do not puppeteer the running game to tick off visual UI checks — the user verifies visually
12. InitMatch's starting state is client-supplied, so story inits enforce a fresh-state guard (score==0, moveIndex==0, max tile <= 64) — otherwise a caller registers a pre-scored board and settles instantly for stars. Exact scenario-board reconstruction (scenario table server-side) is the documented follow-up hardening.
13. The story_progress blob key MUST be created with scope INTERNAL (Storage Blob Keys console tool): internal scope means only snap-to-snap/api-key callers can write while user-auth sessions can still read — this is what makes stars/watermarks server-authoritative. (Supersedes the earlier auth-exemption plan; user-auth writes are a watermark-reset re-farm vector otherwise.)

## Resolved questions
1. **Progress store choice (platform commitment): Storage-snap user json-blob written s2s by the validator (this plan's default — single document, atomic watermark, read-only client) vs modeling each level as a one-time Quests-snap quest (the Daily Missions spec's precedent uses Quests + Remote Config). Both shape provisioning and all later metagame features — needs a call before provisioning.** — _Storage-snap user json-blob, written s2s by the validator (the plan's default). Quests remains the pattern for the daily features — the two coexist separately. Decided 2026-06-12._
2. **Reward economy tuning: concrete per-star and completion amounts per level, and whether the existing story coins = floor(score/10) (validator rewards.ts, marked pending game-design tuning) survives as a base alongside catalog rewards or is fully replaced.** — _Catalog rewards replace floor(score/10) ENTIRELY — the rewards.ts story branch is removed in favor of catalog-driven per-star/completion deltas. Concrete amounts live in content/story_catalog.json and stay tunable there._
3. **Time-requirement semantics: validator wall-clock (created_at → CompleteMatch arrival) is the only forge-proof signal, but it penalizes connection stalls and pauses — accept wall-clock with a tolerance, or defer timed goals to a later pass? (A move-count proxy would change nothing in the engine but alters design intent.)** — _Validator wall-clock (StoredMatch.created_at → CompleteMatch arrival), no tolerance window. A pause mechanic that suspends the timer is planned for a later version — explicitly NOT v1._
4. **v1 content scope: how many worlds/levels at launch, and the exact mapping of the 18 existing scenarios (Tutorial/Amplify/…/Fracture) onto the world map? Genuinely NEW level mechanics require TS-first scenario authoring plus regenerated goldens — out of v1 scope?** — _3 worlds × 15 levels = 45 levels, mapped onto EXISTING scenario sets only (no new TS scenario authoring). World 1 uses only the ice/freeze mechanic; each subsequent world introduces an additional mechanic; difficulty escalates via goal thresholds across scenario repeats._
5. **Offline Story behavior: today Story implicitly requires Snapser sign-in; when offline should the Story button (a) gate with a connect-to-play message, or (b) allow playing the unlocked level with zero stars/rewards/progress recorded?** — _(a) Gate. When offline/unauthenticated the Story button shows a connect-to-play message; no offline story play in v1._
6. **Star display surface: should earned stars/world progress also surface outside story_map (e.g. a Profiles-snap attribute like total_stars next to display_name/avatar_id/title for social surfaces), or stay private to the progress blob for v1?** — _Stars surface only in story_map for v1 — no Profiles attribute or other external surfaces yet._
7. **Should level identity ride in the dormant SynchronizedGameState.level field instead of new wire metadata?** — _No. The hashed SynchronizedGameState is a byte-for-byte mirror of the TS engine; populating even the dormant level field changes golden hashes and breaks parity with the deployed validator and every committed vector. Level identity travels as match-registration metadata instead: InitMatchRequest.level_id → StoredMatch.level_id, echoed back in story_result_json. game/logic/ and the hash domain stay untouched._
8. **Where are stars graded — client or validator?** — _Validator-authoritative. CompleteMatch grades its own validated final state (score, max tile from tiles) plus server wall-clock elapsed time against the catalog goals; the client only renders the returned story_result_json. The progress blob is written s2s-only and read-only to clients, so stars/unlocks/rewards cannot be forged — consistent with the gateway User-Id auth model and careful not to widen the open user-auth self-grant hardening finding._
9. **One content catalog or separate per-surface level definitions (client / validator / Remote Config)?** — _One committed catalog: content/story_catalog.json. It is uploaded verbatim to Remote Config app-config (live content the client fetches), baked into the client at game/story/story_catalog.json (offline/dev fallback), and loaded by the validator for grading. Single source of truth; catalog_version detects drift between the three surfaces._
